# VANTAGE — Vitals / Readiness Corrections
## Date: 2026-08-26
## App version observed: 1.3.10.3

## Purpose

Correct the vitals-import and readiness-calculation faults found in the 26 August 2026 Legs Coach Pack.

The morning vitals supported productive training:

- Recovery: **90%**
- Charge: **90%**
- Rest: **90**
- HRV: **70 ms**
- HRV delta: **+11 ms vs baseline**
- Resting HR: **43 bpm**
- Resting HR status: **at baseline**
- Stress: **0.9 / 3 — Low**
- Status: **Solid**
- Synthesis: **Peak**
- Guidance: **Maintain**
- Blood pressure: **139/72 mmHg**
- Cuff pulse: **51 bpm**

Despite this, the workout Coach Pack calculated:

> **Red — recovery only**

with the reason:

> **Resting HR is well above baseline**

That conclusion is inconsistent with the source vitals.

---

# 1. Critical defect — HRV delta incorrectly copied into resting-HR delta

## Source data

The source vitals state:

- HRV: **70 ms**
- HRV delta: **+11 vs baseline**
- Resting HR: **43 bpm**
- Resting HR: **at baseline**

## Data exported by the workout Coach Pack

```json
"hrv": 70,
"hrvBaseline": null,
"hrvDeltaFromBaseline": 11,
"restingHr": 43,
"rhrBaseline": null,
"rhrDeltaFromBaseline": 11
```

The value **+11** belongs to HRV only.

It must **not** be written to `rhrDeltaFromBaseline`.

### Required correction

If resting HR is explicitly reported as **at baseline**, store one of the following:

```json
"rhrDeltaFromBaseline": 0
```

or, if an exact numerical baseline is unavailable:

```json
"rhrDeltaFromBaseline": null,
"rhrBaselineStatus": "at-baseline"
```

Do not reuse the HRV delta as the RHR delta.

### Acceptance criteria

1. HRV delta and resting-HR delta are parsed independently.
2. `hrvDeltaFromBaseline = 11` must never automatically populate `rhrDeltaFromBaseline`.
3. A source value of **at baseline** must not become **+11 bpm**.
4. Missing RHR baseline data must remain unknown unless the source explicitly provides a delta/status.
5. Import validation must flag impossible duplicate delta mapping across unrelated vitals fields.

# 2. Critical defect — false Red readiness generated from incorrect RHR delta

The Coach Pack contains:

```json
"readiness": {
  "level": "red",
  "title": "Red — recovery only",
  "reasons": [
    "Resting HR is well above baseline"
  ]
}
```

This is based on bad imported data.

The actual source state was:

- Recovery 90
- Rest 90
- HRV +11 vs baseline
- Resting HR at baseline
- Stress Low
- Synthesis Peak
- No symptoms flagged
- BP 139/72

### Required correction

Recalculate readiness only after all vital-field mappings have passed validation.

A missing numerical RHR baseline must **not** itself trigger a red state.

### Recommended rule

If:

- RHR baseline is unknown,
- no positive RHR delta is explicitly supplied,
- and the source states **at baseline**,

then resting HR should be treated as **neutral**, not adverse.

### Expected readiness for this dataset

The exact app label can follow the existing readiness engine, but this dataset must **not** resolve to Red on the basis of resting HR.

Expected result should be broadly equivalent to:

- **Green / productive training allowed**, or
- the normal readiness category generated by Recovery 90 / Rest 90 / low stress.

# 3. Readiness contradiction must generate a validation warning

The report currently says:

- Recovery: **90%**
- Rest: **90**
- Stress: **0.9 Low**
- HRV: **70 ms / +11**
- Resting HR: **43 bpm**
- Readiness: **Red — recovery only**

Yet the Coach Pack reports:

> **Vitals-linkage warnings: None**

This should not happen.

### Required correction

Add a cross-field sanity check before readiness is finalised.

Examples that should raise a warning:

- Recovery >= 80 but readiness = Red.
- Rest >= 80 but readiness = Red.
- HRV above baseline while Red reason claims poor HRV.
- RHR source says `at baseline` while readiness reason says `well above baseline`.
- Synthesis = Peak while readiness = recovery-only.
- Low stress + high recovery + no symptoms but Red readiness.

### Suggested warning

```text
Readiness conflict detected:
Resting-HR readiness reason conflicts with imported source status.
Review vitals mapping before applying training restriction.
```

The app may still calculate Red when genuinely justified, but the contradiction must never pass silently.

# 6. Importer must not silently discard unsupported vitals fields

If the vitals Markdown contains a valid field that the current app schema does not understand, the importer should not simply drop it without notice.

### Required behaviour

For every imported field:

- parsed successfully -> save it;
- recognised but uncertain -> save with confidence/status;
- unsupported -> add import warning;
- malformed -> reject that field and state why.

Example:

```json
"importWarnings": [
  {
    "field": "sleepSummary",
    "reason": "Unsupported nested structure",
    "action": "Current sleep summary was not imported"
  }
]
```

Silent data loss makes readiness errors much harder to diagnose.

# 7. Baseline handling needs explicit states

Current export shows:

```json
"baselineStatus": {
  "hrv": "unknown",
  "restingHr": "unknown"
}
```

while simultaneously storing:

```json
"hrvDeltaFromBaseline": 11,
"rhrDeltaFromBaseline": 11
```

That is internally inconsistent.

### Required baseline states

Use explicit states such as:

- `known`
- `at-baseline`
- `above-baseline`
- `below-baseline`
- `unknown`

A delta may only be used if:

1. a numerical baseline exists, or
2. the source explicitly supplies that delta.

Never manufacture one from another metric.

# 10. Weight-change sanity handling

Current scale reading:

- 25 Aug: **93.1 kg**
- 26 Aug: **89.0 kg**
- Difference: **-4.1 kg**

The vitals notes correctly identify this as short-term fluid/glycogen/gut-content/scale variability rather than tissue loss.

### Required app behaviour

When day-to-day weight changes exceed a configurable threshold, display a data-quality/context flag rather than interpreting the whole change as body-tissue change.

Suggested trigger:

```text
Absolute daily weight change >= 2.0 kg
```

Suggested message:

```text
Large day-to-day weight change detected.
Treat as probable hydration/glycogen/gut-content or measurement variability until confirmed by trend.
```

Do not automatically reject the reading; preserve it and flag it.
